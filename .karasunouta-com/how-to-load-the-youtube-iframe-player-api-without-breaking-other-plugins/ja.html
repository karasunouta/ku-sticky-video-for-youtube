WordPress向けのプラグインを開発している際、多くの方が一度は直面するのがプラグイン同士の競合です。先日、投稿内のYouTube動画をスクロールに応じて画面の隅に追従させるプラグイン（KU Sticky Video for YouTube）を開発していたときのこと。ローカルのクリーンなテスト環境では完璧に動作し、「よし、これで完成だ！」と胸を張っていました。

しかし検証の舞台を自作の別のYouTube系プラグイン（未公開）や、他の動画系プラグインが有効化されているマルチプラグイン環境に移したとたん、事態は一変しました。直前までスムーズに動いていた追従機能はピクリとも動かずに沈黙し、ブラウザのコンソールを開くとそこにはいまいましい赤いエラー文字が。なんてことだ。

でもこれは、プラグイン開発では「よくあること」に過ぎません。そして競合の原因によって、解決方法もさまざまなのが現実です。今回は、YouTube系プラグインの多くが依存するYouTube Iframe APIがマルチ環境下で引き起こす「主導権争い」のメカニズムと、その問題を回避して他のスクリプトと相乗りし共存化を実現するためのJavaScriptの設計について紹介します。

なぜ競合する？ YouTube APIの主導権争い

YouTube動画をJavaScriptから高度に制御するには、公式のYouTube Iframe Player APIをロードする必要があります。一般的な解説記事では、以下のような実装が紹介されているかと思います。

// APIスクリプトをロード
const tag = document.createElement('script');
tag.src = 'https://www.youtube.com/iframe_api';
const firstScriptTag = document.getElementsByTagName('script')[0];
firstScriptTag.parentNode.insertBefore(tag, firstScriptTag);

// ロード完了時に呼ばれるグローバル関数を定義
window.onYouTubeIframeAPIReady = function() {
    const player = new YT.Player('player-id', {
        events: {
            'onStateChange': onPlayerStateChange
        }
    });
};

一見何の問題もないコードですが、WordPressのように複数のプラグインやテーマが非同期に動く環境では、このソースが問題を引き起こします。単純な話、もし他のプラグインがまったく同じように window.onYouTubeIframeAPIReady を定義していたらどうなるでしょう？JavaScriptの性質上、後から実行されたプラグインの処理によって、先に定義されていた初期化関数は丸ごと上書きされて消えてしまいますよね。

結果として、先にロードされた側のプラグインは「APIのロード完了」を検知できず、永遠に起動しなくなってしまうのです。初期バージョンのKU Sticky Video for YouTubeが動かなくなってしまったのもそのせいです。

解決へのアプローチ: いかにしてプラグイン同士の「喧嘩」を避けるか

この競合を防ぎ、あらゆる環境で安全に動作させるために、KU Sticky Video for YouTubeプラグインには以下のような対策を取ることにしました。

1. 非同期ロードの隙間を埋める「スクリプト存在チェック」

YouTube APIのスクリプト読み込みが完了すると、ブラウザのグローバル空間（window）に window.YT というオブジェクトが自動的に生成されます。この window.YT は、YouTubeプレイヤーの生成や操作を行うためのAPIのすべての機能（実態）が格納されているオブジェクトです。

そのため、単純に「window.YT が存在しなければAPIスクリプトをロードする」というチェックをしてしまいがちですが、これだけだと「他のプラグインがタグを挿入した直後で、まだネットワークロード中（window.YT はまだ未定義）」のタイミングで、二重にスクリプトタグが挿入されてしまいます。これを防ぐため、DOMツリー上にすでにYouTube APIのスクリプトが存在するかどうかも併せて確認します。

// URLの表記揺れ（iframe_api / player_api）を考慮して部分一致で検索
const alreadyLoading = document.querySelector(
    'script[src*="youtube.com/iframe_api"], script[src*="youtube.com/player_api"]'
);
if ( ! window.YT && ! alreadyLoading ) {
    // ここで初めてスクリプトタグを挿入する
}

💡 コラム：なぜ ! window.YT と ! alreadyLoading の両方が必要なのか？
一見すると「DOM上にスクリプトタグがあるか（alreadyLoading）」のチェックだけで十分に見えます。しかし、他プラグインが player_api という別の公式URLでロードしていたり、Vite等のビルドツール経由でJS内にAPIを直接バンドルしてロードしている場合、DOM上に iframe_api のタグは存在しません。そのため、すでにロードが完了していることを100%保証する window.YT と、まさに今非同期ロードしている途中の隙間を埋める alreadyLoading（URLの表記揺れに対応したセレクタ）の二重チェックが最も堅牢な防壁になります。

2. window.YT.get() による「イベントの相乗り（バインド）」

すでにページ内のYouTube iframeに対して他者が YT.Player インスタンスを生成していた場合、自前で new YT.Player を二重に実行するとエラーになります。 YouTube APIのグローバルメソッドである window.YT.get() を使い、すでに作成済みのプレイヤーインスタンスを取得して、そこにイベントリスナーだけを「相乗り」させてもらいます。

ここで注意したいのは、**YT.get() の公式な引数は「iframeのID文字列」**だということです。ID属性が無い場合に備え、非公式ながら互換性の高い「DOM要素渡し」をフォールバックに備えた2段構えのバインド処理を組むのが安全です。

let existingPlayer = null;
if ( window.YT && typeof window.YT.get === 'function' ) {
    const id = iframeElement.id;
    // IDがあれば公式仕様で取得。無ければDOM要素渡しでフォールバック
    existingPlayer = ( id ? window.YT.get( id ) : null ) || window.YT.get( iframeElement );
}
if ( existingPlayer ) {
    // 既存インスタンスにイベントを相乗り
    // ※YouTube APIのaddEventListenerは、DOM標準と違って 'on' プレフィックス（onStateChange）が必要です
    existingPlayer.addEventListener('onStateChange', function(event) {
        handlePlayerStateChange(event);
    });
} else {
    // 誰も初期化していなければ、自分が第一発見者として新規作成
    const player = new window.YT.Player(iframeElement, { ... });
}

3. 先客のコールバック関数を破壊せずにラップする

もし他プラグインによって window.onYouTubeIframeAPIReady がすでに定義されていた場合、それを無視して上書きするのではなく、いったん変数に退避させてから実行されるようにラップします。

const previousOnReady = window.onYouTubeIframeAPIReady;
window.onYouTubeIframeAPIReady = function () {
    // 他のプラグインの初期化処理があれば、まずそれを実行してあげる
    if ( typeof previousOnReady === 'function' ) {
        previousOnReady();
    }
};

「あれ？ ここで自分自身の初期化処理も続けて呼び出せばいいのでは？」と思われるかもしれません。一般論として、単に競合を避けて自身の処理を実行するだけであれば、このラッパーの中で previousOnReady() に続けて自身の初期化関数を呼び出せば動作します。

しかし、今回のケース（KU Sticky Video）ではあえてここでは呼び出さず、後述する「ポーリング（定期監視）」側に自身の初期化を完全に委ねています。これには以下の2つの理由があります。

  1. APIがすでにロード済みの場合に対応するため： もし他プラグインによってすでにAPIの読み込みが完了している状態で自プラグインがロードされた場合、onYouTubeIframeAPIReady は二度と実行されません。ラッパーだけに頼ると、自プラグインの初期化自体がスキップされるリスクがあります。
  2. 他プラグインの初期化完了（相乗り）を待つため： 先に説明した通り、他プラグインがAPI Ready直後に非同期でプレイヤーインスタンスを生成する場合、ミリ秒単位のタイミングのズレで YT.get() による相乗りが失敗し、二重生成エラーになることがあります。そのため、他プラグインの初期化が完了するのを少し「待つ」必要があります。

そのため、ここでのラッパー定義は自分自身のためではなく、「もし自プラグインがAPIスクリプトをロードしたことでAPI Readyが発火した際、他プラグインのコールバックを握り潰さずに実行してあげる」という他者への安全弁（セーフティネット）としてのみ機能させています。

実際の共存初期化ロジック：ポーリングによる制御

ここまでに紹介した「ラッパー」「二重ロード防止」「イベントの相乗り」という3つのアプローチを綺麗に噛み合わせるには、初期化処理を実行する絶妙なタイミングのコントロールが必要です。

そこで役立つのが、プログラム側から定期的に状態をチェックしに行く「ポーリング（Polling）」という設計パターンです。

ポーリングとは、「対象の準備はできたか？」と一定の間隔（例えば100ミリ秒ごと）で繰り返し状況を問い合わせ、条件が満たされた段階で処理を実行する監視手法のことです。JavaScriptでは、主に setInterval を用いて実装します。

「他プラグインのロード完了を待って相乗りする」「APIがすでにロード済みならすぐに実行する」といった、相手の出方に左右される非同期処理も、このポーリング監視をハブにすることで、エラーを起こさず安全にタイミングを制御できるようになります。

これらをすべて組み合わせた、実際の初期化コードが以下になります。

function initPlayingMode(iframes) {
    // 1. すでに他スクリプトが挿入済みかも含めてチェックし、APIをロード
    if ( ! window.YT && ! document.querySelector( 'script[src*="youtube.com/iframe_api"], script[src*="youtube.com/player_api"]' ) ) {
        const tag = document.createElement( 'script' );
        tag.src = 'https://www.youtube.com/iframe_api';
        const firstScriptTag = document.getElementsByTagName( 'script' )[ 0 ];
        firstScriptTag.parentNode.insertBefore( tag, firstScriptTag );
    }
    // 2. 先客のコールバックを退避させてラップ
    const previousOnReady = window.onYouTubeIframeAPIReady;
    window.onYouTubeIframeAPIReady = function () {
        if ( typeof previousOnReady === 'function' ) {
            previousOnReady();
        }
    };
    // 3. APIのロードと「他プラグインの初期化完了」をポーリング監視
    let attempts = 0;
    let apiReadyAttempts = 0;
    let setupCompleted = false;
    const checkInterval = setInterval( () => {
        attempts++;
        const isApiReady = window.YT && typeof window.YT.Player === 'function';
        if ( isApiReady ) {
            apiReadyAttempts++;
        }
        // すべてのiframeに対して他者がインスタンス生成を終えたかチェック
        let allFound = false;
        if ( isApiReady && typeof window.YT.get === 'function' ) {
            allFound = true;
            for ( let j = 0; j < iframes.length; j++ ) {
                const id = iframes[ j ].id;
                const player = ( id ? window.YT.get( id ) : null ) || window.YT.get( iframes[ j ] );
                if ( ! player ) {
                    allFound = false;
                    break;
                }
            }
        }
        // 終了条件の判定
        // - 他プラグインによるバインドが完了した (allFound)
        // - または、APIのロード完了を確認してからさらに他プラグインの初期化を待つ猶予時間（300ms）が経過した (apiReadyAttempts >= 3)
        // - または、最大タイムアウト（3秒）に達した (attempts >= 30)
        const shouldStop = allFound || apiReadyAttempts >= 3 || attempts >= 30;
        if ( shouldStop ) {
            clearInterval( checkInterval );
            if ( ! setupCompleted ) {
                setupCompleted = true;
                // 0〜100msのランダムなジッター（遅延）を挟んでからセットアップを実行する
                // 同じ仕組みの別プラグインが同時に初期化しようとした場合の生成衝突を防ぐため
                const jitterDelay = Math.random() * 100;
                setTimeout( () => {
                    setupPlayers( iframes );
                }, jitterDelay );
            }
        }
    }, 100 );
}

💡 なぜ300ms（3回ループ）待つのか？ と「ジッター」による衝突回避の限界

APIの準備完了後、すぐに自前でプレイヤーを初期化するのではなく、300msの「譲歩時間（他プラグインへの待ち時間）」を設けています。もし他プラグインが非同期にプレイヤーを生成しようとしている場合、その完了を少し待ってから「相乗り」することで、二重生成のエラーを防ぐためです。

しかし、これはあくまで「確率的な衝突回避」であり、理論上の競合確率を完全にゼロにするものではありません。他プラグインも全く同じ仕組み（固定の300ms待延）を採用していた場合、タイマーの同期によって同時にプレイヤーの新規作成（new YT.Player）が走り、二重生成エラーが起きるリスクがごく稀に残ります。また、一度二重生成されてしまうと、YouTube APIの仕様上、片方を後から destroy() で破棄しようとしても、生存しているはずのもう片方のプレイヤーまでDOMの書き換えによって巻き添えで破壊されてしまいます。

この衝突確率をさらに極限まで下げるために、本実装では初期化の実行前に「ランダムジッター（0〜100msのランダムな遅延）」を挟むアプローチをとっています。実行タイミングに「揺らぎ」を与えることで、同じ仕組みのプラグインが同時に読み込まれた場合でも、先行した側がプレイヤーを作成し、遅れた側は YT.get() でそのインスタンスを検知して安全に相乗りできるようになります。YouTube API側にプラグイン間の完全な同期用イベントが用意されていない現状において、これが複数プラグインの共存を支える現実的な限界であり、かつ最も堅牢なベストプラクティスと言えます。

おわりに

プラグインにおいてYouTubeのようなメジャーな外部サービスのAPIを使うということは、必然的に競合の可能性を抱え込むことを意味します。

ユーザーは自分の記事にYouTube動画を埋め込み、そこにさまざまなカスタマイズを施す。そのために複数のYouTube系プラグインを併用することは当然想定されます。

それを見越して、YouTube系プラグインにおいてはAPIを競合なく使える実装は不可欠の課題となります。

今回開発した 「KU Sticky Video for YouTube」、および有料版の 「KU Sticky Video for YouTube Pro」 もまた、開発時の検証プロセスでこうしたコンフリクト問題を徹底的に洗い出し、クリアしてぶじリリースに至りました。
